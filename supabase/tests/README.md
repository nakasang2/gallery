# DBの検証（素のPostgresで回す）

```bash
npm run test:sql                      # 全migration + 全テスト
npm run test:sql -- 0042_notifications # 1本だけ
npm run test:sql -- --pending 0036     # 「0035まで適用済みのDB」に0036以降を3回当て、schema.sql と一致するか
```

必要なもの: **postgresql 16**（Supabaseは要らない）。macOS は `brew install postgresql@16`。
`initdb` が PATH に無ければ `PGBIN=/opt/homebrew/opt/postgresql@16/bin` のように渡す。

## なぜ要るか

このリポジトリの守りの**大半はDBの中**にある — RLSポリシー、`security definer` の
トリガ、購入台帳を数える番人。**型チェックもビルドも画面も、それらが正しいかを何も
言わない。** 実際に起きたこと:

- **0041 は「未ログインの来場者から公開サイトが全滅する」状態で push された。**
  ポリシーが呼ぶ関数の実行権限を `authenticated` にしか渡しておらず、`anon` が
  `galleries` を読むだけで落ちた。テストは35項目あったが**全部 `authenticated` で
  走っていた**ので気づかなかった。
- **0039+0040 は「2回流すと、後の番号が消した列が前の番号で復活する」状態だった。**
  1回しか流していなかったので出なかった。

どちらもここで流せば数十秒で出る。

## 書き方の約束（踏んだ罠がそのまま規則になっている）

1. **未ログイン（`anon`）の経路をケースに入れる。** 実トラフィックのほぼ全部がそれ。
   RLSを触ったら「公開ギャラリーが読める／いいねが押せる／記帳できる」を必ず確かめる。
2. **各ファイルは自己完結**させる。他のテストや `seed.sql` に依存しない。土台は
   **番人に通る正しい経路**で作る（例: 無料の1室目は `work_cap <= 5`、2室目以降は
   購入台帳の行を先に入れてから `slots_included = true` で作る）。購入無しで直接
   insert すると番人が正しく弾き、それを実装の失敗と読み違える。
3. **必ず1行返す形で書く。** `select 式 from … where 条件` は該当行が無いと**0行＝無言**
   になり、`t` でも `f` でもないので**合格に見える**。`coalesce(bool_and(…), false)` を使う。
4. **拒否の確認は「持ち主の席」から数える。** 他人の行を消せないことを確かめるとき、
   撃った本人の席から数えると**RLSで見えないので0件**が返り「消えた」と読める。
   `reset role` してから数えるか、影響件数（`UPDATE 0`）を読む。
5. **仕込みは `set local role` の前に置く。** 管理者ロールのまま fixture を書くと
   update ポリシーが無くて0行更新になり、仕込めていないまま検査が走る。
6. **`anon` に切り替えるときは JWTのクレームも消す。** `reset role` はロールだけを戻し、
   `request.jwt.claim.sub` は残る ── そのままだと anon でも `auth.uid()` が直前の人を
   返し、所有者ポリシーが通ってしまう。`set local role anon;` の直後に
   `set local "request.jwt.claim.sub" = '';` を必ず書く（これを忘れて「未ログインから
   下書きが見える」と誤診しかけた）。
7. **エラーを期待するケースは1つずつ `savepoint` で囲む。** 囲まないと、その1件が
   取引を汚して**以降の全項目が `is aborted` で流れなくなる**（実際に38項目が全滅した）。
   型: `savepoint e; <文>; rollback to e; release e;`
8. **fixture を `savepoint` の中で作って巻き戻さない。** あとの項目がその行を数えるなら、
   巻き戻すと「無いもの」を数えて期待外れになる。
9. **エラーを `grep -v` で捨てない。** 捨てた1行が「0001 の途中で止まった」だった
   ことがあり、後半が未適用のDBを相手に検査していた。
10. **外部コマンドの成否をパイプの中で判断しない。** `psql … | grep -v NOTICE || true` は
   **パイプラインの終了状態が最後の `grep`／`true`** になるので、`ON_ERROR_STOP=1` を
   付けていても migration の失敗が消える（2026-08-10: 0047 が途中で落ち、表だけ消えて
   関数とポリシーが残った半端なDBを相手に44項目を検査していた）。出力は変数で受けて
   `if ! out=$(…)` で自分で見る。

## 判定

判定は **`scripts/sql-verdict.mjs`**（`run.sh` が psql の出力を渡す）。落ちたものとして
数えるのは2つ:

- **`f`** — 期待外れ。ラベルと同じ行に出た `f`（`01 なにか: f`）と、**行頭に単独で出た
  `f`** の両方を見る。
- **`is aborted`** — 想定外のエラーが後続を全部巻き込んだ合図。

`ERROR` そのものは数えない — 拒否の確認では**期待している**から。

**判定をシェルの grep から node に出したのは、判定そのものを試験できるようにするため。**
`npm run check:gates` が合成した出力を流して、上の2つを本当に検出するか・`ERROR` や
`off` のような語を誤検知しないかを確かめる。番人が2回続けて嘘をついた履歴があるので:

- `is aborted` を見るようにしたのは、0043 のテストが土台不足で全滅しているのに
  「すべて期待どおり」と表示したため（2026-08-09）。
- **行頭単独の `f`** を見るようにしたのは、`\echo -n 'ラベル: '` と値のあいだに
  `INSERT 0 1` が挟まると値が次の行に落ち、`grep -E ': f$'` を素通りしたため
  （2026-08-10。0046 のテストが期待外れ2件を抱えて「すべて期待どおり」と出た）。

**検証が嘘をつくのは、検証が無いより悪い。**
