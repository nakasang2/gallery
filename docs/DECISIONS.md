# DECISIONS

## 2026-07-29 購入時の承諾は自分のモーダルで取る（Stripe画面には出さない）／文は法が要る2点まで削る
- 背景: ユーザー報告「まだStripeでエラーが出る」＋ダッシュボードのログ。本番の決済セッション作成が400で、応答は「**custom_text cannot be used with Managed Payments**, which is enabled by default on your account」。支払いボタンの上に出していた注意文が丸ごと拒否されていた。2026-07-27 の `tax_code` と同じ Managed Payments（Stripeが販売者＝MoRとして各国の税を代行）由来で、今度は「足したものが許されない」側。
- 決定1（**A案: 注意文を外す。Managed Payments は維持**）: ユーザー選択。`custom_text` を削除し、`managed_payments[enabled]=false` は選ばない — **文言1つのために世界の税の代行から降りる判断ではない**（降りれば消費税/VATを自前で負い、前回足した `tax_code` も無意味になる）。`consent_collection` も逃げ道にならない（ダッシュボードに規約URLの設定が要り、無ければ黙って効かない）。
  - **承諾そのものは元から自分のモーダルで取っている**（チェックが入るまでCTAが進まない）。Stripe画面の一文はその重複だったので、失うのは重ねての表示だけ。承諾を通った事実は `metadata.consent = 'immediate-access-waiver'`（metadataは制約の対象外）としてStripeの購入記録に残す。
  - **今後 `checkout.sessions.create` にUI系のオプション（`custom_text`・`consent_collection`・`custom_fields` 等）を足すときは、実装前に Managed Payments 対応可否を確認する**（LESSONS「決済（Stripe）」×2）。
- 決定2（**A案: 承諾文を法が要る2点まで削り、残りは規約リンクへ**）: ユーザー提案「termsに同じ文があるのだから『規約に同意します』で良いのでは」に対し、**「規約に同意します」には畳めない**ことを説明した上での選択。EU/UKでは即時提供のデジタルコンテンツについて、①今すぐ提供してほしいという明示の請求 ②それにより撤回権を失うことの了解 を、**規約への同意とは別の行為として**取る必要がある（規約に埋めた形は承諾として成立しない）。規約第5条自身が「購入時に別途確認します」と書いており、その仕組みを消すことになる。
  - 文言はこの2点だけに削り、返金の扱いは規約リンクへ逃がす: en `Unlock it now — I give up the 14-day right to cancel.` / ja `今すぐ有効にします — 14日間の返品・解約の権利を放棄します。`（11言語すべて短縮。従来の「有効化後は返金されない」の節は落とした）
  - リンク（`purchase.termsLink`）は**チェックボックスの `<label>` の外**に置く — 中に入れるとリンクを踏むたびにチェックが入れ替わる。`target="_blank"` にして、規約を読んでも購入の文脈を捨てないようにする。
- 却下: 「規約に同意します」だけにする案（EU/UK購入者について撤回権の放棄が成立せず、解放後でも14日以内の返金請求が通り得る。規約第5条と特商法ページの記述も実態と食い違う）。文言を今のまま残す案（ユーザーの「長い」という指摘に応えない）。
- 検証: tsc / check:i18n（**10言語100%・727キー**）/ check:css / check:schema / check:gates / クリーン本番ビルド。**購入モーダルは `/me` と3Dパネル（どちらもサインイン必須）にしか出ないので、本物の `PurchaseModal` を描くだけの一時ページを作って実操作した**（このリポジトリの前例と同じ手法。検証後に削除）— ①1280幅の英語・日本語とも承諾文が1行に収まる ②375幅（実機相当）でも2行 ③**ラベル文字を押すとチェックが入り、規約リンクを押してもチェックは変わらない**（`checked` を実測）④未チェックのままCTAを押すと従来どおりチェックボックスが金色に縁取られ、金色の警告が出る。**実カードでの購入完了はローカルでは検証できない**（Stripeキーが無く501で止まる）。**リンクが新しいタブで開くかはプレビューでは確認できない**（ペインは `target="_blank"` を同じタブで開く）。

## 2026-07-29 値を挟む文は1キーに収め、強調だけを差し込む（`TextWithSlot`）
- 背景: 「穴埋めお願い / まだ必要かも含めて」（ユーザー指示）。番人を広げたら、`/reset` と `/signup` の案内文が「日本語のキー＋英語の地の文」で1文を組み立てていた（日本語では半分だけ英語）。素直に直すと「文の前半キー ＋ `<b>{email}</b>` ＋ 文の後半キー」という**連結**に戻ってしまう — これは 2026-07-29 に `{unit}` で否定した形。
- 決定: **文はひとつのキーに収める。太字などの強調は、訳文の中のプレースホルダの位置で文を割って差し込む**（`components/I18nProvider.tsx` の `TextWithSlot`）。`translate()` は渡されなかったプレースホルダをそのまま残すので、`t('auth.confirmSent')` を**置換せずに**受け取り、`{email}` で `split` して間に `<b>` を挟む。
  - 語順は言語が決められる（日本語・韓国語はアドレスから始まり、英語・独語は文の途中に来る）。実際に11言語で `{email}` の前後を実測した。
  - 訳文がプレースホルダを落とすと差し込む値が文から消えるので、**プレースホルダの取り違えを番人にした**（`check:i18n`。英語を基準に、同じキーの訳文が同じ名前・同じ数の `{…}` を持つかを照合。導入時 7,318 キー×言語の照合で0件）。
- 却下: 文を2キーに割って連結する案（語順・助詞・語形変化を英語に固定してしまう）。太字を諦めて1キーにする案（確認すべきアドレスが本文に埋もれる）。

## 2026-07-29 配置図は枠で囲わない／部屋の全枠を出し、容量超過分は鍵付きで売る
- 背景: ユーザー指示2件 — ①「placement ですが、枠で囲うのなしにしませんか」②「すでに展示されてる作品、空スロットしか表示されていませんが、空スロットすべて表示しませんか。そうすれば5枠埋まっていて、さらに空のスロット押下すると購入させることができます」。**どの間取りも物理スロットは15枠**（`lib/limits.MAX_WORKS_PER_ROOM`、DECISIONS 2026-07-24）だが、無料の容量は5枠で、地図は**使える5枠しか描いていなかった**ため「部屋がまだ広い」という事実が画面に一度も出ていなかった。
- 決定:
  - **①外側の囲みだけ消す**（`.place-map` の枠線・角丸・薄い背景・padding）。部屋の輪郭線とスロットのマスは残す（境界は間取りの線に任せる）。ユーザー選択は3案のうち「外側の囲みだけ」。
  - **②地図に15枠すべて描き、容量を超えた枠は鍵付きにする**。押すと**その枠に届くのに必要な枚数**を初期値にした購入モーダルが開く（`PurchaseModal` の `quantity.initial` を新設）。容量は balanced fill order の前から順に開くので、**「7番目の枠を押したから7枠買う」が嘘にならない**（順序の前方一致は単調なので、買った枠が別の場所に化けることはない）。
  - **買っても届かない枠は出さない**。`MAX_WORKS_PER_ROOM` を超える位置（カスタム間取り＋中央壁だけが16枠になる）は鍵を出しても行き止まりなので非表示。
  - 既に作品が掛かっている枠は容量の外にあっても常に表示・編集可（旧アレンジの固定を殺さない）。
- 併せて直した既存の不具合（②で15枠すべて描いたことで表に出た）: **地図上の描画位置を、作品が向いている方向へ 0.5m ずらす**。中央壁の表裏は 0.52m しか離れていないのに1辺1.25mのマスを描いていたため、**island 間取りは15枠のうち13マスしか描かれず、重なった2組は下のマスを押せなかった**。ついでにタップ判定の「隣までの距離の90%」をユークリッド距離から**軸ごとの距離（チェビシェフ）**に変えた — 判定は軸並行の正方形なので、角を挟んだ斜めの隣は「遠いのに重なる」（hall で2組・island で4組が実際に重なっていた）。ずらし量は下限（中央壁の 0.52m を割る＝0.37以上）と上限（portrait の角の組 1.85m を割らない＝0.6以下）の間で 0.5 に決めた。
- 検証: 4プリセット＋カスタム72通り（hw 6値 × hd 6値 × 中央壁有無）を `lib/presets` をコンパイルして総当たりし、**マスの重なり0・判定の重なり0・描画枠外0**。ずらし量を 0（元の実装）に戻すと island が2組で落ち、0.7 にすると portrait が2組で落ちる**変異テスト**で、この検査が空振りでないことを確認。ブラウザ側でも `getBoundingClientRect` で同じ5レイアウトを実測して一致。**実際の `/me` のカードでも確認した**（`GalleryCard` を一時的に export してモックのストアで描画する検証ページを作り、375px で 15枠・鍵10個・囲みなし、遠い鍵を押すと購入モーダルが「7枠 $3 × 7 = $21」で開くところまで実操作 → 検証ページと一時 export は削除済み）。
## 2026-07-29 選べる選択肢を先に並べる（無料開放されているものを左に）
- 背景: 「初期状態ですでに無料開放されてるものは、全部左に表示してほしい」（ユーザー指示）。テーマは `chic`（有料）が先頭で、無料の `White Cube` は2番目、間取りも有料の `Single Hall` が先頭だった。**最初に目に入るのが買わないと使えないもの**という並びになっていた。

## 2026-07-29 単位の名詞を `{unit}` で差し込むのをやめる — 各言語の文に語を直接書く
- 背景: 購入モーダルの数量ステッパー周りが `{unit}` に単位の語（`purchase.slot`）を差し込む作りで、**5言語で壊れていた**。`translate()` を直接呼んで11言語×count=1/2/10 を出して確定した症状:
  - **de `slot: 'Plätze'`・it `'posti'` は複数形の語**だったので、単数の文が「1 Plätze mehr」「Aggiunge 1 posti」になった。この2言語は単数の文と複数の文が同一だったため、同日の複数形フォールバック修正（`d8f53d7`）の前後どちらでも壊れていた。
  - **es / pt-br は `{unit}s` と語尾にsを足していた**ので「2 lugars」（正しくは `lugares`）。`howMany` と `fewerAria` / `moreAria` も同じ。`d8f53d7` で count=1 だけは直り、count=2 が残っていた。
  - **ko は単複ではなく助詞が壊れていた**（`걸이을` → 正しくは `걸이를`）。`걸이` は母音で終わるので目的格助詞は `를`。**これは単数・複数を書き分けても直らない**種類の不一致で、`{unit}` という設計そのものが原因。
  - 語尾sで正しく複数になるのは en / fr だけだった。
- 決定: **`{unit}` の差し込みをやめ、各言語の文に単位の語を直接書く**。`purchase.optionDesc` / `optionDesc_other` / `howMany` / `fewerAria` / `moreAria` を言語ごとに自然な単数・複数で書き、単位の語だけを持っていた `purchase.slot` を削除した。`PurchaseModal` の `quantity` から `unitLabel` を外し、呼び出し側（`app/me/page.tsx`）も1行減った。
  - **前提が最初から成り立っていなかった**: `{unit}` は「単位が複数種類ある」想定の作りだが、`unitLabel` を渡す呼び出しは**枠（slot）の1か所だけ**だった。抽象の代金だけ払って、その抽象が扱えない語形変化を各言語に押し付けていた。
  - **将来ほんとうに2種類目の単位が来たら、単位ごとにキーを分ける**（プレースホルダに戻さない）。語形変化・助詞・語順は言語側に委ねるしかない — 同日の `presets.frameOf` で「プレースホルダで語を挟む文は、単語を並べて作らない」と決めたのと同じ理由。
  - 各言語の単数/複数: en `slot`/`slots`・fr `emplacement`/`emplacements`・de `Platz`/`Plätze`・it `posto`/`posti`・es `lugar`/`lugares`・pt-BR `lugar`/`lugares`・id `tempat`（単複同形）・ja `枠`・ko `걸이`・zh-Hans/zh-Hant `作品位`。
- **ついでに直した2件**（どちらも `{unit}` 版から続く既存の不具合）: ①**日本語の助数詞**が `{count}つ` で、和語の「つ」は1〜9までしか使えないのに `MAX_WORKS_PER_ROOM = 15` なので**「10つ」という非文が実際に出ていた** → 助数詞を「枠」そのものにして `{count}枠` に（1枠・10枠とも成立）②id の `fewerAria` / `moreAria` が `{unit}` 始まりで**小文字で始まる読み上げラベル**になっていた（`tempat lebih sedikit`）→ `Kurangi tempat` / `Tambah tempat`。
- 却下: 単位ごとに `_one`/`_other` を持つ「単位の辞書」を作る案 — 単位が1種類しかない今は表を1つ増やすだけで、助詞の一致（ko）は依然として解けない。`Intl.PluralRules` に単位側の語形も引かせる案 — 語形変化の表を自前で持つことになり、翻訳者が文を直せなくなる。
- 検証: tsc / check:i18n（直書き0件・状態文言0件・複数形の相方0件・**10言語100%・722キー**）/ check:css / check:schema / check:gates（48件）/ クリーン本番ビルド。`translate()` 直呼びで11言語 × count=1/2/10 の実出力を確認。**実UIでも確認した** — 数量ステッパーは `/me`（サインイン必須）にしか出ないので、**検証用に `SettingsPanel` の購入モーダルへ一時的に `quantity` を渡して本番ビルドで実操作し**（このリポジトリの前例と同じ手法）、日本語で 1枠 → 3枠 → 10枠（合計 `$3 × 10 = $30`）、ドイツ語で **n=1「1 Platz」／n=2「2 Plätze」** を実測してから一時変更を戻した。
- 未解明（既存項目に追記）: 検証中に**購入モーダル操作の直後にプレビューのタブが `/en` へ飛ぶ現象が2回**。`beforeunload` / `popstate` / `submit` / `pushState` / `replaceState` を全部計測しても**1件も発火せず**、`<form>` はどのファイルにも無くステッパーは `type="button"` なので**フォーム送信は静的に否定できた**。ただし**今回は本番ビルドでも起きた** — 2026-07-29 の記録にある「本番ビルドの計測中は一度も起きていない」という前提は誤り。読み取りを別の呼び出しに分ければ最後まで通るので、計測側の制約として扱う。

## 2026-07-29 複数形の単数は「素のキー」でも `_one` でもよい — ただし素のキーを読むのは `one` のときだけ
- 背景: ユーザー報告「英語など複数形を区別する言語で、count が 1 のときに複数形の文が出る（"1 works" と読める）」。`translate()` のフォールバックが `_one → _other → 素のキー` の順で、辞書の多くは**単数を素のキーに書いて複数だけ `_other` を付けている**ため、`resetPerWork_one` が無い → 次に `_other` を見る → **素のキー（＝単数）には構造上決して到達しない**。該当8キー。単数の訳文は11言語すべてに最初から存在していたのに、1つも表示されていなかった。
- 決定: **A′（`translate()` の鎖を形ごとに分ける）**。ユーザー選択。
  - `one` のときは `_one → 素のキー → _other`、**それ以外の形は `_form → _other → 素のキー`**。素のキーは単数なので、`few`/`many` に単数の文を出さないため飛ばす。**fr / es / pt-br / it は今すでに `many` を持つ**（CLDR。10^6 以上で選ばれるので実際の作品数では踏まないが、スラブ系言語を足した瞬間に効く）。
  - **辞書の書き方は2通りを許す**（素のキー＋`_other` ／ `_one`＋`_other`）。88行のキー名変更（B案）はしない。B案では `translate()` 側の穴が残り、次に誰かが素のキーで単数を書いた瞬間に再発する。

## 2026-07-27 CDN配信のCORSを「相手によって変えない」形にする（読み取り`*`＋Transform Rule）
- 背景: R2移行後、3D展示だけ作品が空の額縁になる不具合が**2回**起きた。1回目はブラウザキャッシュのCORS汚染で、`<img>`全16箇所に`crossOrigin="anonymous"`を付けて解決した（LESSONS 2026-07-27）。**同日、同じ症状が再発**。今度はシークレットウィンドウでも直らず、かつ**Claude側の環境では再現しなかった**。
- 真因: 汚染されていたのは**CloudflareのCDNキャッシュ**。CDNは1つのURLに実質1つの応答しか持たない（`Vary`は`Accept-Encoding`以外あてにならない）のに、R2の応答は**リクエスト次第で中身が変わる**ため噛み合っていなかった:
  1. R2は**`Origin`ヘッダが付いたリクエストにしか**`Access-Control-Allow-Origin`を返さない。クローラー／OGP取得／`curl`など`Origin`なしの取得が先に来ると、**許可ヘッダの無い応答**がキャッシュされ、以降そのURLは全員に許可ヘッダなしで配られる。
  2. 旧ポリシーは`AllowedOrigins`にwwwとapexを列挙していたため、応答が**オリジンごとに違った**。wwwで入ったキャッシュがapexの閲覧者に配られてやはり失敗する（本番はwww/apexが両方生きている）。
  3. **キャッシュは配信拠点ごとに独立**なので、**特定の地域の人だけ壊れる**。開発者の環境では正常に見え、再現しない。
- 決定（ユーザー選択 = A案）: **配信元の応答を相手によって変えない**。2段構えで、どちらもCloudflare側の設定変更のみ（コード変更なし）:
  - **R2バケットCORSを2ルールに分割**し、**読み取り(`GET`/`HEAD`)は`AllowedOrigins: ["*"]`**にする。応答が1種類になるので、どのキャッシュが配られても正しい。バケットは元々公開なのでセキュリティは下がらない。**書き込み(`PUT`)は自分のオリジンだけに限定を維持**（アップロード先は`cdn.xibit360.art`ではなくS3 APIエンドポイントなので、読み取りの緩和は書き込みの防御に影響しない）。副次的に、**埋め込み(`?embed=1`)が設定追加なしで任意のサイトから動く**ようになった。
  - **Cloudflare Transform Rule（Modify Response Header）で`Access-Control-Allow-Origin: *`を無条件にセット**（`http.host eq "cdn.xibit360.art"`）。`Origin`なしの応答にはR2が何も付けないため、①だけでは穴が残る。**Transform Ruleは配信の出口で適用されるので`cf-cache-status: HIT`にも効き、既に汚染されたキャッシュごと救える**のが決め手。
  - 動作は`Add`でなく**`Set`**（上書き）。`Add`だとR2の返すヘッダと二重になり、ブラウザは重複を理由に**全部拒否**する。
- 却下: キャッシュのパージだけで済ませる案 = 次にクローラーが来た時点で再発するため。Cache Keyにオリジンを含める案 = Cloudflareでは**Enterpriseプラン限定**。画像を自前ドメイン経由で中継する案 = R2に移った目的（egress無料）を失うため。
- 検証: `Origin`あり／なしの両方で`access-control-allow-origin: *`が返ることを実測、ヘッダが1本だけ（重複なし）であることも確認。実ブラウザで公開ギャラリーの3作品が3D描画され、コンソールエラーゼロを確認。
- 運用メモ: **切り分け用の素の`curl`は`Origin`なし＝汚染側のキャッシュを自分で作る**（今回の調査中に実際にやった）。調査時は`-H "Origin: …"`を付ける。
- 対象: Cloudflare設定のみ（コード変更なし）。手順は docs/R2_SETUP.md §5 / §5.1 に反映。

## 2026-07-27 容量制限の実測化（R2の実バイト数を正とし、署名分を短時間だけ予約する）
- 背景: R2移行でクォータ判定はブラウザからサーバー（`/api/upload-url`）へ移ったが、**判定の材料が`artworks.bytes`の合計のまま**だった。この値はクライアントの言い値で、しかも作品ファイルは「行を作る前」にアップロードされる。監査で認証済みユーザーが300MB上限を無制限に踏み越えられる経路が3本見つかった:

  3. **音声ガイド(15MB)とBGM(15MB)はどこにも記録されない**。署名時に数えるだけなので`storageUsed`は永遠に増えない。作品行はいくつでも作れるため、行の数だけ15MBが積める。

  - 上の3本は**同時に塞がる**。行を作らずに上げたファイルも、偽装した`bytes`も、音声/BGMも、すべて「R2に実在するバイト数」という1つの数字に等しく現れるため。

## 2026-07-27 削除した作品のCDNキャッシュを、削除時にCloudflareへパージさせる
- 背景: R2移行後、**DBとR2からは即座に消えるのに、CloudflareのCDNキャッシュには最大4時間残る**穴が判明（移行中に、削除済みオブジェクトが片方のcoloから200/`cf-cache-status: HIT`で返るのを実観測）。URLを知っている人はその間ダウンロードできる。`app/privacy`の「Deleting a work removes its files from storage」と`app/terms`のテイクダウン対応の記述に対して、実態が追いついていない状態だった。

- 決定（ユーザー選択 = A案）: **削除の直後にCloudflareのキャッシュパージAPIを呼ぶ**。エッジTTLを短くする案（B）や、窓を受け入れてプライバシーポリシーに明記する案（C）は却下。
- 設計判断:
  - **パージはURL指定でなく「プレフィックス（フォルダ）指定」**。調査の結果、プレフィックス指定は**無料プランでも使える**（かつては上位プラン限定だった）。利点は2つ — ①削除したキー一覧を集める必要がなく、`{uid}/{作品ID}/`の1回でdisplay.jpg/thumb.jpg/video/guideを全部カバーできる ②**クエリ文字列を問わずマッチする**ので、アバター/ロゴ/BGMの`?v=タイムスタンプ`付きURLにも届く（URL指定では過去に発行した全タイムスタンプを知らないと不可能）。
  - **順序はR2から消した「後」**。先にパージすると、パージ〜削除完了の隙にアクセスが来てエッジが再キャッシュしてしまう。
  - **ベストエフォート**（例外を投げず`false`を返す）。ファイルは既に消えているので、パージ失敗＝従来の4時間の窓に戻るだけで、データ損失にも削除失敗にもならない。ユーザーの削除操作を失敗させる理由にしない。
  - **`removed > 0`のときだけ呼ぶ**。実体が無かったIDにはキャッシュも無いうえ、存在しないIDの連打で**アカウント共有のパージレート上限（無料プランは毎分5回）**を消費されるのを防ぐ。
  - **未設定でも501にしない**。R2の5変数は「未設定なら壊れたURLをDBに永続化する」ためfail-closed（501）だが、パージは追加の防御層でしかないので、未設定なら黙って無効化する。
- 権限とENV: 既存のR2トークンは**オブジェクト権限のみ**でキャッシュ操作ができないため、**ゾーン権限（Zone → Cache Purge → Purge）の新規APIトークンを1本**発行する。`CLOUDFLARE_ZONE_ID` / `CLOUDFLARE_PURGE_TOKEN` の2変数をユーザーがVercelに設定（`NEXT_PUBLIC_`でないので再デプロイ不要）。手順は docs/R2_SETUP.md §7.5。
- 残る既知の穴（許容）: **すでに閲覧者のブラウザに入ったコピー**は同じ`max-age=14400`で最大4時間残る。パージはCloudflare側にしか効かない。これを縮めるならアップロード時に`CacheControl: 'max-age=300, s-maxage=14400'`（ブラウザ5分/エッジ4時間）を付ける手があるが、「その人がすでに見た画像」であって第三者が新規取得できる経路ではないため、今回は見送り。
