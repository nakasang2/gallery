## 2026-07-29 特商法ページは日本語のときだけ案内する（言語別URLからも外す）
- 背景: 「特商法は日本だけ必要？だったら導線も ja のときだけ用意したらいい気もする」（ユーザー）。
- 事実整理: 特定商取引法は**日本の法律**で、日本語版が法的に効く版。一方で「日本だけ必要」と「他国では何も要らない」は別。**ドイツ語のフッターは `Impressum` と表示して特商法ページを指していた** — 日本向けの開示を、ドイツの義務の名前で案内している状態だった。
- 決定: **`/legal` を言語別URLの対象から外して単一URLに戻し、フッターの導線は `locale === 'ja'` のときだけ出す**（`LegalLink`）。
  - ページ自体は `/legal` で到達可能なまま。**英語の利用規約が本文で参照している**ので、そのリンクは言語に関係なく残す（購入者が販売者情報に辿れなくなるのは避ける）。
  - `/{locale}/legal` は308で `/legal` へ。sitemap も1本だけ（47URL）。9言語の `footer.legal` は未使用になるので削除した。
- 理由: ①日本語版が正なので11言語に増やすと「どれが正か」を毎ページ断る必要がある ②訳す予定のない英語ページのURLを11本作っても検索上の価値がない ③日本以外向けの開示が必要かは**法務の判断**で、その答えが出てから**その国向けのページを作る**方が、日本向けページを流用するより正しい。
- **要確認（法務）**: EU等に販売する場合、その国の事業者情報開示（独 Impressum 等）が別途必要になる可能性がある。Claudeは弁護士ではないので判断していない。

## 2026-07-28 404ページを作る（案A・1画面完結）
- 背景: `app/landing.css` には**最初のコミットから完成した404デザイン**（`.notfound` / `-code` / `-title` / `-lead` / `-cta`）が入っていたが、`app/not-found.tsx` が無いため**実際の404はNext.js標準の真っ白なページ**だった。同日の掃除（`a15237c`）で**この5ルールは削除され、基準線は空配列になった**。そのとき「LPの世界観に合わせた404を作るかは別途判断」として起票されたのが本件。
- 決定: **`app/not-found.tsx` を追加し、削除された `.notfound*` のCSSを実装と同じコミットで戻す**（案A）。ナビとフッターは出さず、CTA2つ（`/` と `/explore`）だけを置く1画面完結の構成。
  - ナビを載せない理由は美観ではなく機能: `.nav` は `opacity: 0` で始まり、`LandingEffects` がスクロール40px超で `.scrolled` を付けて初めて現れる。404は1画面ぶんの高さでスクロールが発生しないため、**ナビを置いても永久に見えない**（`className="nav scrolled"` と決め打ちすればLP側の挙動と二重管理になる）。
- **基準線は空配列のまま**（`scripts/css-dead-baseline.json` = `[]`）。戻したのは実際に描画されるページが使う6ルールだけなので、死んだCSSは1件も増えない。**CSSと、それを使うマークアップを同じコミットに入れる**のが要点で、これを分けると「書いてあるのに効いていない」状態を自分で作ることになる。
- 注意: `check:css` は **CSS→マークアップの片方向**しか見ない（存在しないクラスへのCSSは落とすが、**存在しないCSSを参照するマークアップは検出しない**）。掃除済みのクラス名をマークアップで使っても番人は通ってしまうため、CSSを戻し忘れると無地の404が静かに出荷される。
- 波及: `notFound()` の呼び出しは既に7箇所ある（`app/[handle]` の作家/展示/カタログ、`app/articles/[slug]`）。**非公開化・削除された展示のURLを踏んだ来場者も全員ここに来る**ため、文言は「リンクが変わった」だけでなく「展示が非公開になった可能性」にも触れている。
- 却下: **ナビ＋フッター付き**＝回遊先は増えるが上記のとおりナビを決め打ちする必要があり、LPのスクロール挙動と二重管理になる。**404を作らず5ルールを削除**＝基準線は同じだけ減るが、真っ白な標準ページのままで、作家が共有したURLが死んだときの体験が最悪になる（このサービスは共有リンクが入口）。
- 検証: `/nope/deeper/still`（ルート不一致）と `/this-room-does-not-exist`（`[handle]` の `notFound()` 経由）の両方で **HTTP 404** を確認。日本語/英語（`Accept-Language` とCookieの両方）で表示確認、1280px・375px・320pxで `getBoundingClientRect()` 実測（横あふれなし、CTAは46px＝44px以上、320pxでは折り返す）。`/_not-found` はビルド出力で `ƒ`（動的）— ルートレイアウトが既に `cookies()` を読むためアプリ全体が動的で、`getServerT()` を足しても静的プリレンダとの衝突は起きない。

## 2026-07-28 多言語SEO をやる（「URLに言語を入れない」を撤回）
- 背景: 「多言語SEOはやりたい」（ユーザー）。**2026-07-28 に決めた「URLに言語を入れない」を撤回する**。Cookieで内容が変わる同一URLは、検索エンジンがどの言語版を索引するか選べず hreflang も張れないため、多言語SEOと両立しない。
- 決定1 — **対応言語は11**: ja / en / ko / zh-Hans / zh-Hant / fr / es / de / pt-BR / it / id。既存の組版トークン（latin / cjk）で全て賄えるので**CSSの追加工事はゼロ**。
  - 日本人視点で抜けやすい2つを意図的に入れた: **pt-BR**（SNS利用者数が世界最大級で、イラスト/デザイン系の作家人口が厚い）と **zh-Hant**（台湾・香港。簡体とは用語が違うので別辞書。台湾のアートシーンは活発）。
  - **アラビア語（RTL）は含めない** — 物理CSSプロパティ92箇所の転換と `textures.ts` の文字方向対応が入り、辞書追加とは別の工事になる（B14と同枠）。ロシア語は Stripe の決済制約、ヒンディー/ベトナム/タイは英語で足りる層が厚いため今回は外す。
- 決定2 — **サブディレクトリ方式** `www.xibit360.art/ja/explore`。同一ドメインなのでドメイン評価が分散しない。既存URLは301で既定語（en）へ送る。**実装は middleware での書き換えを第一候補にする** — 17ルートを `app/[locale]/` へ移すと、ルート直下の動的セグメントが `[locale]` と `[handle]` で衝突するうえ、116箇所の内部リンクを全部書き換える大工事になる。
- 決定3 — **言語別URLは自社が書いたページだけ**: `/` `/explore` `/articles` `/articles/[slug]` `/demo` `/legal`。作家ページ（`/@name`・`/@name/[slug]`・カタログ）は**単一の正規URLのまま**にし、UIの文言だけ来訪者のCookieに従う。

## 2026-07-27 CDN配信のCORSを「相手によって変えない」形にする（読み取り`*`＋Transform Rule）
- 背景: R2移行後、3D展示だけ作品が空の額縁になる不具合が**2回**起きた。1回目はブラウザキャッシュのCORS汚染で、`<img>`全16箇所に`crossOrigin="anonymous"`を付けて解決した（LESSONS 2026-07-27）。**同日、同じ症状が再発**。今度はシークレットウィンドウでも直らず、かつ**Claude側の環境では再現しなかった**。
- 真因: 汚染されていたのは**CloudflareのCDNキャッシュ**。CDNは1つのURLに実質1つの応答しか持たない（`Vary`は`Accept-Encoding`以外あてにならない）のに、R2の応答は**リクエスト次第で中身が変わる**ため噛み合っていなかった:
  1. R2は**`Origin`ヘッダが付いたリクエストにしか**`Access-Control-Allow-Origin`を返さない。クローラー／OGP取得／`curl`など`Origin`なしの取得が先に来ると、**許可ヘッダの無い応答**がキャッシュされ、以降そのURLは全員に許可ヘッダなしで配られる。
  2. 旧ポリシーは`AllowedOrigins`にwwwとapexを列挙していたため、応答が**オリジンごとに違った**。wwwで入ったキャッシュがapexの閲覧者に配られてやはり失敗する（本番はwww/apexが両方生きている）。
  3. **キャッシュは配信拠点ごとに独立**なので、**特定の地域の人だけ壊れる**。開発者の環境では正常に見え、再現しない。
- 決定（ユーザー選択 = A案）: **配信元の応答を相手によって変えない**。2段構えで、どちらもCloudflare側の設定変更のみ（コード変更なし）:
  - **R2バケットCORSを2ルールに分割**し、**読み取り(`GET`/`HEAD`)は`AllowedOrigins: ["*"]`**にする。応答が1種類になるので、どのキャッシュが配られても正しい。バケットは元々公開なのでセキュリティは下がらない。**書き込み(`PUT`)は自分のオリジンだけに限定を維持**（アップロード先は`cdn.xibit360.art`ではなくS3 APIエンドポイントなので、読み取りの緩和は書き込みの防御に影響しない）。副次的に、**埋め込み(`?embed=1`)が設定追加なしで任意のサイトから動く**ようになった。
  - **Cloudflare Transform Rule（Modify Response Header）で`Access-Control-Allow-Origin: *`を無条件にセット**（`http.host eq "cdn.xibit360.art"`）。`Origin`なしの応答にはR2が何も付けないため、①だけでは穴が残る。**Transform Ruleは配信の出口で適用されるので`cf-cache-status: HIT`にも効き、既に汚染されたキャッシュごと救える**のが決め手。
  - 動作は`Add`でなく**`Set`**（上書き）。`Add`だとR2の返すヘッダと二重になり、ブラウザは重複を理由に**全部拒否**する。
- 却下: キャッシュのパージだけで済ませる案 = 次にクローラーが来た時点で再発するため。Cache Keyにオリジンを含める案 = Cloudflareでは**Enterpriseプラン限定**。画像を自前ドメイン経由で中継する案 = R2に移った目的（egress無料）を失うため。
- 検証: `Origin`あり／なしの両方で`access-control-allow-origin: *`が返ることを実測、ヘッダが1本だけ（重複なし）であることも確認。実ブラウザで公開ギャラリーの3作品が3D描画され、コンソールエラーゼロを確認。
- 運用メモ: **切り分け用の素の`curl`は`Origin`なし＝汚染側のキャッシュを自分で作る**（今回の調査中に実際にやった）。調査時は`-H "Origin: …"`を付ける。

- 背景: R2移行でクォータ判定はブラウザからサーバー（`/api/upload-url`）へ移ったが、**判定の材料が`artworks.bytes`の合計のまま**だった。この値はクライアントの言い値で、しかも作品ファイルは「行を作る前」にアップロードされる。監査で認証済みユーザーが300MB上限を無制限に踏み越えられる経路が3本見つかった:
  1. **行を作らなければ何も記録されない**。毎回新しいuuidで署名を取り、`artworks`行を挿入しなければ`bytes`は増えないまま、自分のフォルダに無制限にオブジェクトを書ける。
  2. **`bytes`は偽装できる**。行を作る場合でも`bytes: 0`で挿入すれば合計は増えない（DB制約もトリガも無い）。
  3. **音声ガイド(15MB)とBGM(15MB)はどこにも記録されない**。署名時に数えるだけなので`storageUsed`は永遠に増えない。作品行はいくつでも作れるため、行の数だけ15MBが積める。
     - ※音声ガイドのアップロード経路は同日、別セッションが死にコードとして撤去した（`5026a7b`。サーバー側TTSへの置き換えでUIが先に消えていた）。この経路は削除によって塞がったので、本項の修正で実効があるのは**BGM(15MB)**。
  - （軽微）TOCTOU: `used`を読んでから署名するまで何も予約しないので、同時リクエストが全て同じ`used`を見る。
- 前提の確認: 移行前も同程度に露出していた（旧Supabase RLSポリシーも自分のフォルダ内なら任意パスを許可し、クォータ判定はブラウザのみ）。ただし**R2移行前でユーザーデータがまだ1件も無い今が、入れるコストが最も低い**タイミングなので先に塞ぐ。
- 決定（ユーザー選択 = A案）: **使用量の正を「R2に実在するバイト数」にする**。署名のたびにサーバーが`{uid}/`配下をListObjectsV2で実測し、その値で判定する。クライアントの申告値は判定に一切使わない。
  - 上の3本は**同時に塞がる**。行を作らずに上げたファイルも、偽装した`bytes`も、音声/BGMも、すべて「R2に実在するバイト数」という1つの数字に等しく現れるため。
  - **同時実行対策として、署名した分を`storage_reservations`に短時間だけ積む**（migration 0030）。判定は「実測値＋自分の生きた予約」。ファイルがR2に着けば実測値に含まれ、予約は期限切れで自然に消える。
  - **予約の寿命(720秒)は署名URLの有効期限(600秒)より長くする**。R2はPUT開始時にしか期限を見ないので、9:59に始まった転送が10:02まで書き続けることがある。同時に切れると「予約も切れた・LISTはまだ完了していないPUTを見られない」という無防備な数秒ができる。
  - **cronは使わない**。期限切れ行は次の署名要求のついでに消える（`for update skip locked`で他セッションと待ち合わない）。Vercel Hobbyのcronは1日1回までで、掃除まで最大1日かかる構成は避けたかった。
  - **クォータの対象は`{uid}/`配下の全ファイル**（ユーザー選択）。アバター/ロゴ/LP画像も算入する。除外するとキー形状のパターンマッチが必要になり、将来キー設計を変えた日に静かに壊れる。実サイズはアバター約50KB・ロゴ約30KB・LP画像1枚約150KBで300MBに対して誤差。
- 実装メモ:
  - `reserve_storage` RPCは`security definer`＋`search_path=''`。`authenticated`から直接も呼べるが、細工してできるのは**自分の枠を自分で狭めることだけ**: (1)嘘の実測値を渡しても増えるのは自分の予約だけで署名付きURLは1本も出ない（URLを出すのはAPIルートで、そちらは自分でR2を実測する）(2)`greatest()`で予約は増える方向にしか更新できず、小さく上書きして枠を空けられない。
  - ユーザー単位の`pg_advisory_xact_lock`で同時リクエストを直列化する。これが無いと2本が互いの予約が入る前に残量を読み、どちらも通る。
  - **0030未適用でも503にはしない**。RPCが無い場合（PGRST202/42883）は「実測値のみで判定・予約なし」に縮退する。上の3本は塞がったまま、同時実行対策だけが外れる。全アップロードを止めるほうが実害が大きいため。
  - `/me`の使用量メーターも同じ数字を読むよう`GET /api/storage/usage`を新設（旧`getStorageUsage`はブラウザで`artworks.bytes`を合計しており、「12MB使用中」と表示しながらアップロードが拒否される食い違いが起き得た）。
  - `artworks.bytes`は**情報用として残す**（判定には使わない）。列の削除はマイグレーションと挿入経路の変更を伴う割に得るものが無い。
- トレードオフ（承知の上で受け入れ）:
  - 署名1回につきR2へのLISTが1回増える（Class A操作。無料枠100万回/月、1ユーザーのオブジェクトは数十個なので1ページで済む）。
  - アップロード完了後、最大12分は予約と実測値の**二重計上**で使用量が実際より多く見える。安全側（拒否側）に倒れるだけで、上限を超えて通ることはない。commit通知をクライアントに任せる案は「呼ばなければいいだけ」なので却下、掃除ジョブ案はcron必須なので却下。
  - 孤児ファイル（登録に失敗して残ったゴミ）も使用量に算入される。実際にCloudflareへ支払う量と一致するので、むしろ正しい挙動と判断。

## 2026-07-27 削除した作品のCDNキャッシュを、削除時にCloudflareへパージさせる
- 背景: R2移行後、**DBとR2からは即座に消えるのに、CloudflareのCDNキャッシュには最大4時間残る**穴が判明（移行中に、削除済みオブジェクトが片方のcoloから200/`cf-cache-status: HIT`で返るのを実観測）。URLを知っている人はその間ダウンロードできる。`app/privacy`の「Deleting a work removes its files from storage」と`app/terms`のテイクダウン対応の記述に対して、実態が追いついていない状態だった。
- 実測で確定した前提: 本番の`cdn.xibit360.art`は**200応答にも404応答にも`cache-control: max-age=14400`（4時間）**を付けて返す（R2の既定。アップロード時に`CacheControl`を指定していないため）。`s-maxage`ではなく`max-age`なので、**エッジだけでなく閲覧者のブラウザにも4時間残る**。
- 決定（ユーザー選択 = A案）: **削除の直後にCloudflareのキャッシュパージAPIを呼ぶ**。エッジTTLを短くする案（B）や、窓を受け入れてプライバシーポリシーに明記する案（C）は却下。
- 設計判断:
  - **パージはURL指定でなく「プレフィックス（フォルダ）指定」**。調査の結果、プレフィックス指定は**無料プランでも使える**（かつては上位プラン限定だった）。利点は2つ — ①削除したキー一覧を集める必要がなく、`{uid}/{作品ID}/`の1回でdisplay.jpg/thumb.jpg/video/guideを全部カバーできる ②**クエリ文字列を問わずマッチする**ので、アバター/ロゴ/BGMの`?v=タイムスタンプ`付きURLにも届く（URL指定では過去に発行した全タイムスタンプを知らないと不可能）。
  - **順序はR2から消した「後」**。先にパージすると、パージ〜削除完了の隙にアクセスが来てエッジが再キャッシュしてしまう。
  - **ベストエフォート**（例外を投げず`false`を返す）。ファイルは既に消えているので、パージ失敗＝従来の4時間の窓に戻るだけで、データ損失にも削除失敗にもならない。ユーザーの削除操作を失敗させる理由にしない。
  - **`removed > 0`のときだけ呼ぶ**。実体が無かったIDにはキャッシュも無いうえ、存在しないIDの連打で**アカウント共有のパージレート上限（無料プランは毎分5回）**を消費されるのを防ぐ。
  - **未設定でも501にしない**。R2の5変数は「未設定なら壊れたURLをDBに永続化する」ためfail-closed（501）だが、パージは追加の防御層でしかないので、未設定なら黙って無効化する。
- 権限とENV: 既存のR2トークンは**オブジェクト権限のみ**でキャッシュ操作ができないため、**ゾーン権限（Zone → Cache Purge → Purge）の新規APIトークンを1本**発行する。`CLOUDFLARE_ZONE_ID` / `CLOUDFLARE_PURGE_TOKEN` の2変数をユーザーがVercelに設定（`NEXT_PUBLIC_`でないので再デプロイ不要）。手順は docs/R2_SETUP.md §7.5。
- 残る既知の穴（許容）: **すでに閲覧者のブラウザに入ったコピー**は同じ`max-age=14400`で最大4時間残る。パージはCloudflare側にしか効かない。これを縮めるならアップロード時に`CacheControl: 'max-age=300, s-maxage=14400'`（ブラウザ5分/エッジ4時間）を付ける手があるが、「その人がすでに見た画像」であって第三者が新規取得できる経路ではないため、今回は見送り。
- 対象: `lib/cachePurge.ts`(新規), `app/api/storage/delete/route.ts`, `app/api/account/delete/route.ts`, `docs/R2_SETUP.md`。tsc・next build クリーン。**本番での実効確認はトークン設定後**（R2_SETUP §7.5の4ステップ）。

- **番人（検出器）を追加・変更したら `npm run check:gates` を通す**（3回ルール ×4 → 2026-07-28 昇格）。検出器が自分の検査範囲を取りこぼして「0件」が嘘になったことが4回ある（i18nのpathspec `**` で `app/page.tsx` が漏れた／`accept="image/*"` をコメント開始と誤認し270行抜けた／未追跡ファイルを見ていなかった／`check:css` がIDセレクタとカンマ列挙の非最終行を見ていなかった）。どれも合成入力を1本流せば即分かるものだったので、`scripts/check-gates.mjs` が一時gitリポジトリを作って本番の番人をそのまま走らせ、**落ちるべき入力が落ちること**と**生きているものを誤検知しないこと**の両方を検査する。番人を変えたら、その変更で守れるようになった入力をケースとして足す。手順書ではなく機械にしたのは、同じ判断を×3〜×4で手順書が止められなかった実績があるため。

## 2026-07-23 床の白い写り込みの構造的封じ込め＋影のリアリティ（距離濃度・軟らかい際）

## 2026-07-23 影消失の真因修正＋チラつき対策（MSAA）
- 背景: ユーザーFB「読み込み直後だけ影が表示されすぐ消える」「白い写り込みがまだある」「ワイヤーや反射がチラつく」。
