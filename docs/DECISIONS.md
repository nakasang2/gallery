# DECISIONS

## 2026-08-09 展示のURLは `xibit360.art/expo/{slug}` — サブドメインを撤回してパスにする
- 決定（ユーザー判断「URLですが xibit360.art/name-of-expo/ じゃだめですかね / サブドメインが hobby だと難しい気がする」）: 展示の公開URLは **`xibit360.art/expo/{slug}`**。直下の 2026-08-09「展示ごとのサブドメイン」を**この項が上書きする**。
- 撤回の理由は**運用コストが展示数に比例すること**、証明書ではない。サブドメイン方式は動くところまで作って**実機で確認済み**（`tokyo-expo.xibit360.art` を Vercel のドメイン追加＋Cloudflare の `CNAME`(DNS-only) で 200 OK）。ただし**展示1件ごとに手作業が2つ**増え、Hobby の**1プロジェクト50ドメイン**という天井もある。パスなら追加作業ゼロ・上限なし。
- **ルート直下（`xibit360.art/{slug}`）にしなかった**: ルートにはアプリのルートが14個と言語コードが11個居て、将来のルートとも衝突する。得るのは1階層ぶんの短さだけなので、`/expo/` を1枚挟んで**名前空間を分ける**。予約語（`lib/expoHost` の `RESERVED`）はパスでも必要なので、そのまま流用する。
- **列は作り直さず改名した**（migration 0040）。必要なものは「展示ごとにユニークな名前」で、`profiles.subdomain` はまさにそれ。ただし**パスを駆動するものが `subdomain` という名前のままだと後で読む人が必ず誤解する**ので、`expo_slug` / `set_expo_slug` / `guard_expo_slug` / `profiles_expo_slug_format` / `profiles_expo_slug_key` に揃えた。0040 は**0039 を適用済みでも飛ばしていても同じ結果になる**（改名する枝と新規に作る枝の両方を持つ）ので、0039 を流していない環境は 0040 だけ流せばよい。
- **ホスト解析のコードは消さずに env で切って残す**（ユーザー承認）。`NEXT_PUBLIC_EXPO_DOMAIN` 未設定で `expoSlugFromHost()` が常に null を返し、middleware の書き換えも canonical の組み立ても**パス側に倒れる**。将来サブドメインをやるなら**環境変数とDNSだけで戻せる**（実機で通っている経路を捨てないため）。**今は未設定のまま**にする。
- 実装: `app/_expo/[sub]/` → `app/expo/[slug]/`（`[room]` ごと `git mv`）。`/_expo/` は「書き換え先であってURLではない」ための命名だったが、**パスが本番のURLになったので `_` は嘘になる**。`lib/expoHost` に `expoPath()` を足し、`lib/seo` の `exhibitionUrl()`/`artistUrl()` が `expoHostsEnabled` で `expoUrl()` と `expoPath()` を出し分ける。sitemap も同じ関数を通すので、canonical と sitemap が同じURLを名乗る。
- **一覧へのフォールバックは持たない**（サブドメイン版の判断を継承）: 公開物ゼロの展示 slug は 404 が正直な答え。
- 検証: **0040 を Postgres 16 に流して27項目 × 3経路**（①0039適用済み→0040 ②0039を飛ばして0040だけ ③0040を3回＝再実行安全で索引・制約・トリガが重複しない）。データが改名を越えて残ること、旧名（列・制約・索引・トリガ・関数2本）が消えていること、`guard_expo_slug` が `security invoker` のままで本人の直UPDATEを弾き `service_role` は素通ること、`lower()` ユニークが大文字違いも重複と見ること、空白で剥奪できることを実測。tsc / build / 番人4種（i18n・css・schema・gates）通過、11言語100%。
  - **最初の1回目は全部が vacuous な `t` だった**: ロールはクラスタ共通なので2つ目のDBで `create role authenticated` が "already exists" で落ち、`ON_ERROR_STOP` で harness が `profiles` を作る前に止まっていた。「消えている」系のアサーションは**土台が無いと全部通る**。ハーネスに「`profiles` と種データが無ければ raise」という番人の番人を入れてから再測した（LESSONS 2026-08-09 に記録）。

## 2026-08-09 展示ごとのサブドメイン — ワイルドカードを捨てて「任意の別名」にする
- **※ この項は上の「展示のURLは `xibit360.art/expo/{slug}`」で上書きされた（2026-08-09、同日）。** サブドメインは実機で動くところまで確認したが、展示ごとの手作業と Hobby の50ドメイン上限を理由にパスへ切り替えた。以下は**なぜサブドメインでワイルドカードを使えないか**の記録として残す（env を立てれば戻せる経路の前提でもある）。
- 決定（ユーザー選択）: 展示のURLは **`tokyo-expo.xibit360.art` のサブドメイン**。パス名前空間（`/expo/[slug]`）案は不採用。
- **ワイルドカードは使えない**（ユーザー調査 2026-08-09）: Vercel は `*.domain` の証明書を「ネームサーバーを Vercel に完全移管した場合のみ」発行し、`_acme-challenge` だけを NS 委任する回避策は公式に非推奨（自動更新が保証されない）。このゾーンは `cdn.xibit360.art` が **R2 のカスタムドメイン＝ゾーンが Cloudflare にあることが必須**で、CORS を直す Transform Rule も載っているので移管できない。
- 決定: **サブドメインは1件ずつ実在のホストとして登録する**。ワイルドカードでないので通常の HTTP-01 証明書が発行され、`www` と同じ経路で自動更新される。NS 移管も不要で、Cloudflare ゾーンはレコードを1本足すだけ。
- 決定（設計の要）: **サブドメインは任意の別名**。展示は**常に `/@ハンドル` でも公開され**、サブドメインは canonical と配る先だけを変える。この形にした理由が3つ:
  - Vercel の**1プロジェクト50ドメイン**（Hobby）は「別名の数」の天井であって展示数の天井ではない。尽きても新しい展示は `/@ハンドル` で普通に公開できる
  - `/expo/[slug]` の名前空間を**作る必要が無くなった** — パス側のURLは `/@ハンドル` として既に存在しているので、それが退路を兼ねる
  - `NEXT_PUBLIC_EXPO_DOMAIN` 未設定で機能ごと切れるので、プレビュー環境が「届かないホストを canonical に書く」事故を起こさない
- **認証クッキーの心配は外れた**（当初の懸念を撤回）: `lib/supabase.ts` は素の `createClient` で `@supabase/ssr` を使っておらず、セッションは **localStorage**＝クッキーではない。広げるものが無いので認証は無変更。裏返しに **localStorage はオリジンごと**なので、サブドメインは**来場者専用の公開面**になり、作家の編集と未公開プレビューは本ドメイン（`/me`・`/@ハンドル/部屋`）に残る。**だから `/@ハンドル` をリダイレクトで潰せない**（前回「1本に寄せる」と書いたのを撤回）。canonical はサブドメイン、`/@ハンドル/...` も動かし続ける＝編集用と配布用の分離。
- 実装:
  - `lib/expoHost.ts` に**ホスト解析と予約語**を集約。middleware は**文字列処理だけ**でDBを触らない（全リクエストの前にラウンドトリップを置きたくない）。`tokyo-expo.xibit360.art/painting` → `/_expo/tokyo-expo/painting` に書き換え、解決は書き換え先のルートで `cache()` 付きで行う
  - **入れ子は拒否**（`a.b.xibit360.art` を `b` として扱わない＝なりすまし防止）。`www`/`cdn`/`api`/`_acme-challenge` など**予約語は付与も解決も拒否**（`cdn` を渡したら R2 配信が死ぬ）
  - `/_expo/...` は**書き換え先であってURLではない**ので、sitemap にも入れず何もリンクしない。**一覧へのフォールバックは持たない** — 公開物ゼロの展示ホストは404が正直な答え
  - **付与は管理者だけ**（`set_expo_subdomain`・`guard_subdomain`）。行だけ先に書き換わると「DBには入っているが届かない別名」ができ、**canonical が死んだURLを指す**。本人が自分で取れるUIは後回し（ユーザー指示「今のところ仕組みだけ」）
  - ユニークは **`lower(subdomain)`** で張る（DNSは大小を区別しないので、`Expo` と `expo` を別行で持てると片方が届かない別名になる）
  - `fetchAll` に**フォールバック列**を追加。あれはエラーで break して**それまでの分を返す**ので、`profiles` に新しい列を足すと 0039 未適用のDBで**ユーザー一覧が丸ごと空になる**（degrade ではなく消滅）。1件も読めていないときだけ狭い列で再試行する
- 検証: **ホスト解析を31ケース実測**（通常/ポート付き/大文字/本体/www/**cdn**/入れ子/別ドメイン/Vercelプレビュー/予約語/長さ/punycode、名前検査、URL組み立て、middlewareの書き換え先）。**SQLは Postgres 16 に schema.sql ごと適用して7ケース**（本人の書き換え=拒否／非管理者のRPC=拒否／管理者の付与=OK／重複=ユニーク違反／**大文字違いも重複扱い**／形式違反=拒否／空文字で剥奪して名前が再利用できる）。tsc / build / 番人4種 通過、11言語100%。
- **ユーザー作業**: `NEXT_PUBLIC_EXPO_DOMAIN=xibit360.art` を Vercel に設定。展示ごとに ①Vercel のドメインに `sub.xibit360.art` を追加 ②Cloudflare に `CNAME sub` → `cname.vercel-dns.com`（DNS-only）。**ワイルドカードのレコードは作らない**。頻度が上がったら付与時に両APIを叩く自動化を足せる（`VERCEL_API_TOKEN` / `CLOUDFLARE_API_TOKEN`）。

## 2026-08-09 作者は作品ごと・板の作家欄は部屋の中身から導出する
- 背景: 合同展示の相談中に見つけた事実 — `fetchPublicExhibition` は作者名を**ギャラリーの所有者**から取り、全作品に同じ名前を配っていた（`rowToArtwork(row, ownerName)`）。他人の作品を掛けられるようにした（0037）だけでは、**プレートも構造化データも全部主催者の名前になる**。合同展示は作者名が違うことが最低条件なので、これが実質的な前提工事だった。
- 決定1（**作者は作品ごと**）: placements の埋め込みを `artworks (*, profiles (...))` に広げ、**作品の所有者のプロフィール**から名前を取る。`artworks.owner_id → profiles` のFKに乗るだけで、`profiles_select_all` は `using (true)` なので追加のポリシーは要らない。埋め込みが解決できない場合（PostgRESTのスキーマキャッシュ等）は従来どおり部屋の所有者を配る＝合同展示より前の全部屋では正しい答え。
  - **配管1本で5箇所が直った**: 3Dの名板（`textures.ts` の byline）・鑑賞ドロワー・印刷カタログ・平文リスト（クローラ向け）・構造化データの `creditText`/`copyrightNotice`。どれも既に `art.artist` を読んでいたので、出どころを直すだけで正しくなった。
- 決定2（**板の作家欄は導出**・ユーザー承認）: タイトルウォールと `InfoPanel` の「作家」は、**その部屋に掛かっている作品の所有者から導く**（`lib/roomPlan.roomExhibitor`）。所有者が1人なら**その作家**（名前・ハンドル・バイオ・アイコン）、複数なら**アカウント（団体）**。
  - **形態を宣言させない**のが狙い。①1室=1作家 ②混在 ③テーマ別×混在 ④1作家が複数室 ⑤個人の多室 のどれでも正しくなり、1つの展示の中で①と②を混ぜても成立する。新しい列もUIも要らず、部屋の中身を変えれば板が追随する。
  - 「1人の部屋だが板は団体名で出したい」は導出では出せない。部屋のタイトルは部屋ごとの自由文なので見出しでは表現できる。**上書きの列は、実際に要望が出てから足す**。
- 決定3（**構造化データも作品ごと**）: `creator` は作品ごとの Person を指し、参加作家ぶんの `Person` ノードを graph に出す。以前は1ページ1つの `personId` を全作品に振っていたので、**混在展示だと全作品が主催者の作品としてGoogleに登録される**（誤った著作者の主張であり、作家が合同展に出る動機そのものを捨てていた）。`personNode` は `/@ハンドル#person` で @id を振るので、作家が衝突せず、複数部屋にまたがる同一作家は1エンティティにまとまる。
- 既知の限界: 団体アカウントも `Person` として出る（`Organization` が正確だが、アカウントが個人か団体かを区別する列が無い）。区別する必要が出たら足す。
- 検証: `roomExhibitor` と `exhibitionJsonLd` に**合成した部屋を流して15項目を実測**（`npx tsx`）。①単独=その作家＋バイオもその人／②混在=団体＋作品ごとに別のcreator＋Personノード3つ（2作家＋aboutが指す主催者）＋@idが全部ユニーク／③空=団体／④埋め込み無し=部屋の所有者にフォールバック。**最初は「混在ならPersonは2つ」と書いて落ちたが、間違っていたのは期待値のほう**（主催者は `CollectionPage.about` が指す先として graph に居る必要がある）。tsc / build / 番人4種 通過。

## 2026-08-09 動画のストレージ上限は 300MB のまま据え置き
- 背景: 多室（$25/室）を出したことで、1人が複数の部屋に動画を置けるようになった。`PLAN.storageBytes` は 300MB/アカウントで**部屋数と無関係**なので、動画（1本 `PLAN.videoBytes` = 40MB）は実質**7本で上限**。画像は §11.4 の実測が約0.34MB/点なので60点でも20MB程度で当たらない。
- 決定（ユーザー判断「一旦300MBで」）: **据え置き。増やさない。** ビデオパス保有者だけ別枠にする案は採らない。
- 理屈: 動画の原価は**再生数に比例する変動費**（§11.4 — Cloudflare Stream 1,000分あたり約$1）で、保管容量とは別の軸。容量を先回りで増やすと、変動費側の上限管理が無いまま入口だけ広げることになる。**詰まった声が出てから、どちらの軸で緩めるかを決める**のが順序として正しい。
- 効いてくる先: 多室と動画を両方買った人が最初に当たる。`/help` の「動画は展示できますか？」は `PLAN.videoBytes` から MB を導出しているので文言は自動追随するが、**「7本まで」という含意はどこにも書いていない**（容量の残りはダッシュボードのメーターに出る）。

## 2026-08-09 無料枠のロンダリングを塞ぐ（等級を行に持つ）
- 背景: ユーザー指示「ロンダリングは塞ぎたい」。0036 の番人は「部屋が1つも無ければ5枠、あれば15枠」という**作成順の推定**でキャパを決めていて、行には「これが無料枠だった」という記録が無かった。**部屋を買う → 元の無料部屋を削除 → 作り直す** と、作り直した部屋が「2室目以降」に見えて15枠で作られる（無料の5枠が15枠に化ける・$30相当・1回）。
- **なぜ既存の情報では塞げなかったか**（採用案の理由でもある）: 既存行のキャパから推定する案（「最大キャパの部屋が購入数より少ないあいだだけ15枠を出す」）は、**$3スロットで15枠まで育てた無料部屋と買った部屋が完全に同じ姿**になるので誤検知する。誤検知の向きが悪く、**$25払った人に5枠の部屋を渡す**事故になる。台帳側でも紐付けられない — `record_capacity_purchase` は行の `item_key` を Checkout セッションにしているので、スロット購入がどの部屋のものか後から分からない。
- 決定: **等級を行に持つ**（migration 0038・`galleries.slots_included`）。「その部屋のキャパが部屋購入に含まれて来たか」の真偽値。部屋数を作成順ではなく**等級で数える**:
  - 有料の部屋は「購入数 > 既存の有料部屋数」のあいだだけ作れる
  - 無料の部屋は「まだ無料部屋を持っていない」ときだけ作れる
  - 合計は自動的に `1 + 購入数` に収まるので、0036 の合計チェックは要らなくなった（`enforce_room_allowance` を差し替え）
  - **購入した部屋を消しても購入は焼けない**（有料の枠が空くだけ・実測12）。**育てた無料部屋は無料部屋のまま**なので買った人が損をしない（実測13-15）
  - **等級は作成時に固定**（`guard_room_grade`）。false→true に書き換えられるなら、無料部屋を有料に化かして購入枠を空け、もう1室作れてしまう（`work_cap` と同じ作法で、`security invoker` にして呼び手のロールを見る）
  - アプリ側は `capForNewRoom(existingRooms)` を捨てて `gradeForNewRoom(tally, roomsPurchased)` に。**有料を先に出す**（払った人がその場で15枠の部屋を得られる。合計はどちらの順でも同じ）
  - バックフィル: 所有者ごとに最古の1室を無料枠、それ以外を有料。0036〜0038 のあいだに作られた部屋は「1室目=5枠/以降=15枠」なので作成順が等級と一致する（本番は1人1室なので実質すべて無料枠）
- 検証: ローカルの Postgres 16 で15ケース実測。**ロンダニングそのものを流して弾かれることを確認**（7 無料部屋を削除→8 有料として作り直す=拒否「購入は使用済み」→9 無料枠で15枠を要求=拒否→10 正直に5枠で作り直す=通る＝**穴だけが閉じて機能は壊れていない**）。加えて 11 等級の書き換え=拒否、12 有料部屋の削除で枠が戻る、13-15 **無料部屋を$3スロットで15枠に育てても等級は無料のままで、次の部屋購入がちゃんと有料部屋を許す**（キャパ推定案が壊れる例そのもの）。

## 2026-08-09 扉は1つ・行き先は扉で選ぶ／特商法とFAQの追随／無断掲載を塞ぐ

## 2026-08-09 展示室を複数にする（$25/室・15枠込み・玄関を1つ決める）
- 背景: ユーザー相談「一室最大15作品だけど、追加料金を払って二室にしたら30作品にできるよね」「二室以上の場合は空間上に連絡通路を設けて移動できるように（部屋間の移動は新規ロードで問題ない）」「2dUI上では部屋がたくさんあっても好きに移動できる」「合同展示のシステムにも応用できそう」。
- 調査で分かった前提（相談時にユーザーへ提示した）:
  - **DBとルートは最初から複数室対応**。`galleries` は owner_id+slug で複数行を持て、`/@name/[slug]` も既にあり、`app/[handle]/page.tsx` は「公開1室なら展示そのもの、複数なら一覧」と分岐済みだった。効いていた制限は `PLAN.galleries = 1` の1箇所だけ。
  - **素で2室にしても30点にはならない**。`createGallery` は `work_cap` に購入時点の `PLAN.worksPerGallery`(5) を継承するので 5+5=10 になる。
  - **レイアウトは既に部屋ごと・所有はアカウント単位**（`galleries.layout` は行の列、`ownedLayoutIds` はギャラリーのスコープを持たない）。「部屋ごとに別のレイアウトを選ぶ／1回買えば全室で使える」はモデル変更ゼロで成立した。
- 決定（ユーザー）:
  - **1室追加 = $25 買い切り・繰り返し可・その部屋の15枠込み**（`PRICE_USD_CENTS.room = 2500`）。**レイアウト/テーマは別売り**のまま（部屋の値段には含めない）。
  - **URLは作家1本のまま**。必ず1つ「玄関（メイン部屋）」を決め、`/@name` はその部屋を描く。サブ部屋は `/@name/[slug]`。canonical も同じ規則（`exhibitionPath` は `publicGalleryCount === 1` ではなく `isMain` で判定するようにした）。
  - **部屋間の移動は新規ロード**。3Dシーンは今までどおり常に1室だけを描く。
  - 合同展示は第2弾。**主催者がハンドルを取り、その配下の部屋として開く**方針（`/expo/[slug]` の新名前空間は作らない）。理由は ①玄関＋サブ部屋の仕組みがそのまま流用できる ②`/@name` の canonical・OG画像・sitemap・hreflang が全部そのまま効く ③`profiles.id` が `auth.users` を直接参照しているため「団体プロフィール」はFKを外す最重量級の変更になる。**URLを決めることと所有モデルを決めることを分離できる**のが決め手。
- 実装:
  - `roomAllowance(roomsPurchased) = PLAN.galleries + roomsPurchased`。**枠は「数」で持ち、部屋は購入後に本人が作る**（webhookは台帳1行だけ書く）。こうすると (a) 決済で半端な部屋が残る経路が原理的に無い (b) 部屋を消しても購入は焼けない (c) 作るときにテーマ/レイアウト/題を自分で選べる。
  - `capForNewRoom`: 1室目=5、以降=15。**購入室は最初から物理上限なので $3/枠のアドオンは購入室に当たらない**（`remaining=0` で checkout が409、UIも `work_cap >= MAX` でボタンを無効化済み）。
  - **番人はDB側に置いた**（migration 0036 のトリガ2本）。`galleries` の insert は RLS 経由でブラウザから直接行われ、`createGallery` の枚数チェックはクライアントが渡した購入数を信じるだけなので、それだけでは**購入ゼロで部屋を無限に作れた**（しかも2室目以降は15枠付き）。`enforce_room_allowance` が購入台帳（webhookしか書けない）を数え、初期 `work_cap` も1室目5/以降15で縛る。`guard_work_cap_raise` は `work_cap` の引き上げを購入経路（security definer のRPC）だけに許す。
  - **満杯の瞬間に2択を並べて出す**（`.me-capacity-offer`）。1部屋目を5→15にするのは 10×$3=$30、新室は15枠込みで$25 なので、**容量だけ見れば新室のほうが安い**。片方だけ見せると「先に$30払った人が後で気づく」瞬間ができるので、値段は変えず開示だけした。用途は違う（この部屋を濃くする / 2つ目の展示を持つ）。
  - **新しい部屋は「玄関の部屋の見た目」をコピーして開く**（ユーザー決定 2026-08-09、追加）。テーマ/間取り/額の既定/マット/掛け方/キャプション/Design Tools を引き継ぐ。**題とステートメントとカバーは引き継がない**（あれはその展覧会の中身の話で、部屋のデザインではない）。当初は無料の studio テンプレート（whitecube/corridor）で開いていたが、**買った部屋なのに自分のテーマが消えたように見える**。権利はアカウント単位なので切り替えは無料だが、既定を白い部屋にしておく理由が無い。**新たな解錠にはならない** — コピー元は同じ所有者の部屋なので、すでに解錠済みのものしか入らない。`custom` 間取りは `layout_params` も一緒に運ぶ（でないと寸法が既定に戻る）。
  - **新しい部屋は空で開く**。`arrangement` を未設定にすると `placeWorks` がアカウントの作品を0番から自動で詰めるため、買った直後の部屋が隣の部屋と同じ内容で開き、扉が複製へつながってしまう。1室目以外は**明示的な null 配列**（§11.13 の「意図的な空き枠」）で作る。
  - **作品ごとの額装は部屋ごとにした**。従来はストアの `frameOverrides` 等を読み書きしていたが、ストアは `refreshMyGallery`→`getMyGalleryRow`（=玄関の部屋）しか読まないので、**サブ部屋のタブで玄関の値が表示され、サブ部屋の編集が玄関に保存されていた**。`fetchPlacementOverrides(row.id)` を出どころにし、保存も `rebuildPlacements(row.id)`（配置編集と同じ行基準の経路）に変えた。同じ作品を部屋ごとに別の額で飾れるのは多室の趣旨そのもの。
  - **3Dの扉は壁に穴を開けず、床に立つ枠**（`components/gallery/RoomPortals.tsx`）。`Room` の壁は開口部の無い1枚板で、穴を開けると壁ジオメトリ・影のベイク・`clampToRoom` を全レイアウトぶん作り直すことになる。枠＋近接判定なら衝突・影・ゴーストに一切触らない。位置は `layout.entry`（来場者が実際に立つ点）から**側方**に取り、`ENTRY_CLEAR`(2.2m) だけ離した片側に並べる。最大4枚で、それ以上の部屋はHUDの一覧が索引になる。
  - **2DのHUDに部屋一覧**（`RoomSwitch`）。扉の前に立つと行き先の名前が出る。埋め込み（`?embed=1`）では一覧を出さず、扉は新規タブで開く（他人のページのフレームを差し替えないため）。
- 検証（SQL）: **ローカルの Postgres 16 に stub（auth.users / auth.uid / 3ロール）を置いて `schema.sql` を実行し、9ケースを実測**（無料1室目5枠=通る／無料1室目に15枠=弾く／購入ゼロで2室目=弾く／1室購入して2室目15枠=通る／1購入で3室目=弾く／`authenticated` が `work_cap` を上げる=弾く・下げる=通す／購入RPCなら上げられる＋15でクランプ／玄関の二重=部分ユニーク索引が弾く／`set_main_room` が原子的に付け替わる）。**この実測で自分のトリガのバグを1件発見**（`guard_work_cap_raise` を `security definer` で書いたため `current_user` が常に所有者になり番人が素通り→`security invoker` に修正。LESSONS 2026-08-09）。
- 検証（幾何）: **レイアウト5種＋customの両端 × 部屋1/2/3/4/5/8** をスクリプトで全数照合（部屋内・ベンチ/間仕切りと非干渉・扉同士が重ならない・法線が部屋中心を向く `dot=1.000`・spawnから2.20m以上）。**この照合で実際に3件のバグを見つけて直した**（①4枚以上でクランプが扉を同じ位置に積む ②`+PI/2` で全扉が横向き＝真横から見えない ③奇数枚のとき中央の扉がspawn上に立ち、ロード直後に枠の中にいる）。UIは実クラス名の一時QAルートで1280/375を実測（横あふれ0、満杯2択がPCで横並び・スマホで縦積み、部屋タブ・玄関バッジ・部屋一覧・扉プロンプトを目視、pageerror 0件）。QAルートは削除済み。tsc / build / check:i18n / check:css / check:schema / check:gates 通過、11言語100%。

## 2026-08-03 SNSの入力欄は「貼るだけ」にする（フルURL表示・取り違えだけ注意）
- 背景: ユーザー指摘3件 — ①「あそこだけフォームUIが他と違って、白で悪目立ちしてる」②「どこから入力していいか分かりにくい」③「Discordの箇所にInstagram貼ったりなどミスがあった場合のみバリデーション」。
- 原因（①）: 入力欄の見た目は `.me-field input, .me-field textarea, .spotlight-row input` という**セレクタの列挙**で当てており、SNSの欄はそこに入っていなかった。CSSが無い入力欄はブラウザ既定＝白地で描かれる。列挙に足して解決（新しい入力欄を足したらここを見る、とコメントを残した）。
- 決定:
  - **欄には「来場者が開くURL」をそのまま出し入れする**（`https://instagram.com/yourname`）。プレースホルダも完成形のURLにするので「どこから入れるか」を考える余地が消える。左に出していた `instagram.com/` の短冊は廃止。
  - 受け取るのは**フルURL / スキームなし / @付きハンドル / 素のハンドル**のどれでも。欄から離れた時にURLの形へ整える（`instagram.com/yusuke/` → `https://instagram.com/yusuke`、`@yusuke` → `https://x.com/yusuke`）。**保存の形は今までどおりハンドル**なので、公開ページ・`sameAs` 側の変更は無い。
  - **一本道でないプロフィールURLはURLのまま持つ**（`youtube.com/channel/UC…`）。最後の区切りだけ取るとハンドルとして組み立て直せず `youtube.com/@UC…` に化けるため。
  - **取り違えはホストで判定し、注意文だけ出す**（ユーザー選択: 自動で移動はしない）。「{found} のリンクのようです（この欄は {expected} です）」。**注意文は欄から離れた時だけ**出す — 打っている途中の `https://ins` はまだどのホストにも当たらず、live に出すと入力中ずっと赤くなる。
  - **取り違えている間はその欄を保存しない**（空を保存する）。入力は消さずに残す。手で打つと `h` `ht` `htt` … は URL に見えないので通ってしまい、途中の断片が保存値として残るため。
  - **専用の欄を3つ追加**（ユーザー選択）: Bluesky（ハンドル型）、Discord・LINE（**プロフィールではなく招待/友だち追加のリンク**なのでURL型）。公式アイコンは Simple Icons（CC0）。
- 検証: `lib/sns.ts` を単体で16通り、実UIで9通り（一時ページに本物の `ProfileCard` を描いて実操作。検証後に削除）。375pxで横あふれ0。

## 2026-07-30 公開ギャラリーのSEO（B案: 土台＋クロール可能な本文と構造化データ）
- 背景: ユーザー要望「各アーティストがギャラリーを公開したら、その公開ギャラリーもSEO対策された上でindexされるようにしたい」。調査で分かった事実 — **索引される配線（sitemap 全公開ギャラリー・robots.txt・OGカード）は 2026-07-2x に既にできていた**。空だったのは中身で、穴は8件あった。

## 2026-07-27 CDN配信のCORSを「相手によって変えない」形にする（読み取り`*`＋Transform Rule）
- 背景: R2移行後、3D展示だけ作品が空の額縁になる不具合が**2回**起きた。1回目はブラウザキャッシュのCORS汚染で、`<img>`全16箇所に`crossOrigin="anonymous"`を付けて解決した（LESSONS 2026-07-27）。**同日、同じ症状が再発**。今度はシークレットウィンドウでも直らず、かつ**Claude側の環境では再現しなかった**。
- 真因: 汚染されていたのは**CloudflareのCDNキャッシュ**。CDNは1つのURLに実質1つの応答しか持たない（`Vary`は`Accept-Encoding`以外あてにならない）のに、R2の応答は**リクエスト次第で中身が変わる**ため噛み合っていなかった:
  1. R2は**`Origin`ヘッダが付いたリクエストにしか**`Access-Control-Allow-Origin`を返さない。クローラー／OGP取得／`curl`など`Origin`なしの取得が先に来ると、**許可ヘッダの無い応答**がキャッシュされ、以降そのURLは全員に許可ヘッダなしで配られる。
  2. 旧ポリシーは`AllowedOrigins`にwwwとapexを列挙していたため、応答が**オリジンごとに違った**。wwwで入ったキャッシュがapexの閲覧者に配られてやはり失敗する（本番はwww/apexが両方生きている）。
  3. **キャッシュは配信拠点ごとに独立**なので、**特定の地域の人だけ壊れる**。開発者の環境では正常に見え、再現しない。
- 決定（ユーザー選択 = A案）: **配信元の応答を相手によって変えない**。2段構えで、どちらもCloudflare側の設定変更のみ（コード変更なし）:
  - **R2バケットCORSを2ルールに分割**し、**読み取り(`GET`/`HEAD`)は`AllowedOrigins: ["*"]`**にする。応答が1種類になるので、どのキャッシュが配られても正しい。バケットは元々公開なのでセキュリティは下がらない。**書き込み(`PUT`)は自分のオリジンだけに限定を維持**（アップロード先は`cdn.xibit360.art`ではなくS3 APIエンドポイントなので、読み取りの緩和は書き込みの防御に影響しない）。副次的に、**埋め込み(`?embed=1`)が設定追加なしで任意のサイトから動く**ようになった。
  - **Cloudflare Transform Rule（Modify Response Header）で`Access-Control-Allow-Origin: *`を無条件にセット**（`http.host eq "cdn.xibit360.art"`）。`Origin`なしの応答にはR2が何も付けないため、①だけでは穴が残る。**Transform Ruleは配信の出口で適用されるので`cf-cache-status: HIT`にも効き、既に汚染されたキャッシュごと救える**のが決め手。
  - 動作は`Add`でなく**`Set`**（上書き）。`Add`だとR2の返すヘッダと二重になり、ブラウザは重複を理由に**全部拒否**する。
- 却下: キャッシュのパージだけで済ませる案 = 次にクローラーが来た時点で再発するため。Cache Keyにオリジンを含める案 = Cloudflareでは**Enterpriseプラン限定**。画像を自前ドメイン経由で中継する案 = R2に移った目的（egress無料）を失うため。
- 検証: `Origin`あり／なしの両方で`access-control-allow-origin: *`が返ることを実測、ヘッダが1本だけ（重複なし）であることも確認。実ブラウザで公開ギャラリーの3作品が3D描画され、コンソールエラーゼロを確認。
- 運用メモ: **切り分け用の素の`curl`は`Origin`なし＝汚染側のキャッシュを自分で作る**（今回の調査中に実際にやった）。調査時は`-H "Origin: …"`を付ける。
- 対象: Cloudflare設定のみ（コード変更なし）。手順は docs/R2_SETUP.md §5 / §5.1 に反映。

## 2026-07-27 容量制限の実測化（R2の実バイト数を正とし、署名分を短時間だけ予約する）
- 背景: R2移行でクォータ判定はブラウザからサーバー（`/api/upload-url`）へ移ったが、**判定の材料が`artworks.bytes`の合計のまま**だった。この値はクライアントの言い値で、しかも作品ファイルは「行を作る前」にアップロードされる。監査で認証済みユーザーが300MB上限を無制限に踏み越えられる経路が3本見つかった:
  1. **行を作らなければ何も記録されない**。毎回新しいuuidで署名を取り、`artworks`行を挿入しなければ`bytes`は増えないまま、自分のフォルダに無制限にオブジェクトを書ける。
  2. **`bytes`は偽装できる**。行を作る場合でも`bytes: 0`で挿入すれば合計は増えない（DB制約もトリガも無い）。
  3. **音声ガイド(15MB)とBGM(15MB)はどこにも記録されない**。署名時に数えるだけなので`storageUsed`は永遠に増えない。作品行はいくつでも作れるため、行の数だけ15MBが積める。
     - ※音声ガイドのアップロード経路は同日、別セッションが死にコードとして撤去した（`5026a7b`。サーバー側TTSへの置き換えでUIが先に消えていた）。この経路は削除によって塞がったので、本項の修正で実効があるのは**BGM(15MB)**。
  - （軽微）TOCTOU: `used`を読んでから署名するまで何も予約しないので、同時リクエストが全て同じ`used`を見る。
- 前提の確認: 移行前も同程度に露出していた（旧Supabase RLSポリシーも自分のフォルダ内なら任意パスを許可し、クォータ判定はブラウザのみ）。ただし**R2移行前でユーザーデータがまだ1件も無い今が、入れるコストが最も低い**タイミングなので先に塞ぐ。
- 決定（ユーザー選択 = A案）: **使用量の正を「R2に実在するバイト数」にする**。署名のたびにサーバーが`{uid}/`配下をListObjectsV2で実測し、その値で判定する。クライアントの申告値は判定に一切使わない。
  - 上の3本は**同時に塞がる**。行を作らずに上げたファイルも、偽装した`bytes`も、音声/BGMも、すべて「R2に実在するバイト数」という1つの数字に等しく現れるため。
  - **同時実行対策として、署名した分を`storage_reservations`に短時間だけ積む**（migration 0030）。判定は「実測値＋自分の生きた予約」。ファイルがR2に着けば実測値に含まれ、予約は期限切れで自然に消える。
  - **予約の寿命(720秒)は署名URLの有効期限(600秒)より長くする**。R2はPUT開始時にしか期限を見ないので、9:59に始まった転送が10:02まで書き続けることがある。同時に切れると「予約も切れた・LISTはまだ完了していないPUTを見られない」という無防備な数秒ができる。
  - **cronは使わない**。期限切れ行は次の署名要求のついでに消える（`for update skip locked`で他セッションと待ち合わない）。Vercel Hobbyのcronは1日1回までで、掃除まで最大1日かかる構成は避けたかった。
  - **クォータの対象は`{uid}/`配下の全ファイル**（ユーザー選択）。アバター/ロゴ/LP画像も算入する。除外するとキー形状のパターンマッチが必要になり、将来キー設計を変えた日に静かに壊れる。実サイズはアバター約50KB・ロゴ約30KB・LP画像1枚約150KBで300MBに対して誤差。
- 実装メモ:
  - `reserve_storage` RPCは`security definer`＋`search_path=''`。`authenticated`から直接も呼べるが、細工してできるのは**自分の枠を自分で狭めることだけ**: (1)嘘の実測値を渡しても増えるのは自分の予約だけで署名付きURLは1本も出ない（URLを出すのはAPIルートで、そちらは自分でR2を実測する）(2)`greatest()`で予約は増える方向にしか更新できず、小さく上書きして枠を空けられない。
  - ユーザー単位の`pg_advisory_xact_lock`で同時リクエストを直列化する。これが無いと2本が互いの予約が入る前に残量を読み、どちらも通る。
  - **0030未適用でも503にはしない**。RPCが無い場合（PGRST202/42883）は「実測値のみで判定・予約なし」に縮退する。上の3本は塞がったまま、同時実行対策だけが外れる。全アップロードを止めるほうが実害が大きいため。
  - `/me`の使用量メーターも同じ数字を読むよう`GET /api/storage/usage`を新設（旧`getStorageUsage`はブラウザで`artworks.bytes`を合計しており、「12MB使用中」と表示しながらアップロードが拒否される食い違いが起き得た）。
  - `artworks.bytes`は**情報用として残す**（判定には使わない）。列の削除はマイグレーションと挿入経路の変更を伴う割に得るものが無い。
- トレードオフ（承知の上で受け入れ）:
  - 署名1回につきR2へのLISTが1回増える（Class A操作。無料枠100万回/月、1ユーザーのオブジェクトは数十個なので1ページで済む）。
  - アップロード完了後、最大12分は予約と実測値の**二重計上**で使用量が実際より多く見える。安全側（拒否側）に倒れるだけで、上限を超えて通ることはない。commit通知をクライアントに任せる案は「呼ばなければいいだけ」なので却下、掃除ジョブ案はcron必須なので却下。

## 2026-07-27 削除した作品のCDNキャッシュを、削除時にCloudflareへパージさせる
- 背景: R2移行後、**DBとR2からは即座に消えるのに、CloudflareのCDNキャッシュには最大4時間残る**穴が判明（移行中に、削除済みオブジェクトが片方のcoloから200/`cf-cache-status: HIT`で返るのを実観測）。URLを知っている人はその間ダウンロードできる。`app/privacy`の「Deleting a work removes its files from storage」と`app/terms`のテイクダウン対応の記述に対して、実態が追いついていない状態だった。
- 実測で確定した前提: 本番の`cdn.xibit360.art`は**200応答にも404応答にも`cache-control: max-age=14400`（4時間）**を付けて返す（R2の既定。アップロード時に`CacheControl`を指定していないため）。`s-maxage`ではなく`max-age`なので、**エッジだけでなく閲覧者のブラウザにも4時間残る**。
- 決定（ユーザー選択 = A案）: **削除の直後にCloudflareのキャッシュパージAPIを呼ぶ**。エッジTTLを短くする案（B）や、窓を受け入れてプライバシーポリシーに明記する案（C）は却下。
- 設計判断:
  - **パージはURL指定でなく「プレフィックス（フォルダ）指定」**。調査の結果、プレフィックス指定は**無料プランでも使える**（かつては上位プラン限定だった）。利点は2つ — ①削除したキー一覧を集める必要がなく、`{uid}/{作品ID}/`の1回でdisplay.jpg/thumb.jpg/video/guideを全部カバーできる ②**クエリ文字列を問わずマッチする**ので、アバター/ロゴ/BGMの`?v=タイムスタンプ`付きURLにも届く（URL指定では過去に発行した全タイムスタンプを知らないと不可能）。
  - **順序はR2から消した「後」**。先にパージすると、パージ〜削除完了の隙にアクセスが来てエッジが再キャッシュしてしまう。
  - **ベストエフォート**（例外を投げず`false`を返す）。ファイルは既に消えているので、パージ失敗＝従来の4時間の窓に戻るだけで、データ損失にも削除失敗にもならない。ユーザーの削除操作を失敗させる理由にしない。
  - **`removed > 0`のときだけ呼ぶ**。実体が無かったIDにはキャッシュも無いうえ、存在しないIDの連打で**アカウント共有のパージレート上限（無料プランは毎分5回）**を消費されるのを防ぐ。
  - **未設定でも501にしない**。R2の5変数は「未設定なら壊れたURLをDBに永続化する」ためfail-closed（501）だが、パージは追加の防御層でしかないので、未設定なら黙って無効化する。
- 権限とENV: 既存のR2トークンは**オブジェクト権限のみ**でキャッシュ操作ができないため、**ゾーン権限（Zone → Cache Purge → Purge）の新規APIトークンを1本**発行する。`CLOUDFLARE_ZONE_ID` / `CLOUDFLARE_PURGE_TOKEN` の2変数をユーザーがVercelに設定（`NEXT_PUBLIC_`でないので再デプロイ不要）。手順は docs/R2_SETUP.md §7.5。
- 残る既知の穴（許容）: **すでに閲覧者のブラウザに入ったコピー**は同じ`max-age=14400`で最大4時間残る。パージはCloudflare側にしか効かない。これを縮めるならアップロード時に`CacheControl: 'max-age=300, s-maxage=14400'`（ブラウザ5分/エッジ4時間）を付ける手があるが、「その人がすでに見た画像」であって第三者が新規取得できる経路ではないため、今回は見送り。
- 対象: `lib/cachePurge.ts`(新規), `app/api/storage/delete/route.ts`, `app/api/account/delete/route.ts`, `docs/R2_SETUP.md`。tsc・next build クリーン。**本番での実効確認はトークン設定後**（R2_SETUP §7.5の4ステップ）。

## 2026-07-23 3Dギャラリーの陰影realism強化（PC向け・自然/上品）
- 背景: ユーザー「影がない／3Dのリアリティがない」。現状は作品スポットが額縁影を壁に焼き込み＋N8AO接地は入っていたが、影が`PCFShadowMap`(硬い)でCGっぽかった。対象はPC（スマホはLOW_POWERでEffects一式オフ＝別問題、今回は対象外）。

- 残（今回対象外）: スマホは`LOW_POWER`でAO等オフのため平面的なまま。必要なら軽量な接地陰の別途検討。
- **追記 2026-07-23（追い込み）**: ①`shadow-radius 4`はソフトすぎて影が見えづらいFB→**2**へ（くっきり寄り）＋作品スポット`shadowMapSize`を`1024→2048`(PC)で輪郭を明瞭化。ベンチ・額装とも共有で改善。②`PCFSoftShadowMap`は「一番外の枠」だけcastだと中抜けになる件はmat/art面castShadowで対応済（LESSON 2026-07-23）。③**反射床**: 床を`meshPhysicalMaterial`→**drei `MeshReflectorMaterial`**(PCのみ・`LOW_POWER`は従来のclearcoat維持)。作品/ゴースト/室内が床に映り込みリアリティUP。設定=resolution512/blur[320,90]/mixStrength0.55/mirror0.4/roughness0.82で「鏡でなく艶のある木床」。木目はmap/roughnessMap/bumpMapで維持、`receiveShadow`維持でベンチ影も床に出る。/demoで反射・影・エラーなしを実機確認。
- **追記2 2026-07-23（額縁の壁影を参考写真並みに）**: 実シャドウマップは近接マウント＋角度で淡く、参考写真のような明確な落ち影が安定して出せない（3回調整しても弱い）→ **アートディレクションされたソフト影プレーンを併用**（`getSoftShadowTexture`＝ブラー済み暗い角丸／`Exhibit`で作品背後 z0.006・少し下(-0.06)・やや大きめ・opacity0.42）。ライトモード非依存で確実、スマホでも出る。反射は「床より上の全要素」が対象（平面反射なので天井ライト/ベンチ/作品/ゴースト全部映る）＝ユーザー確認質問への回答。実影(bench/floor)は継続。opacity/offset/sizeで調整可。LESSON 2026-07-23参照。
